# futex PI 重排队阶段

在 main 已实现的 raw 202 WAIT_REQUEUE_PI（11）和 CMP_REQUEUE_PI（12）
上，本批补充 Linux 错误顺序、代理 CAS 故障后的源恢复及批量迁移，支持
PRIVATE 与无标记键。完整 futex 和所有 syscall 路径目标继续保留。

等待者使用同一个非零 token，目标键关系和源恢复日志保存为共享数值记录。
迁移前先通知原始 park，再发布目标队列和获取日志；等待者通过已提交状态
判断阶段。代理 CAS 故障或竞争时，源日志恢复原始登记，避免把等待者丢在
错误的队列。已存在的目标等待者始终排在后续迁移的源等待者之前。

KINAKAZE_FUTEX_OPT=0 逐项提交并重新计算捐赠；默认配置批量提交迁移行。
空闲目标的首个代理获取在两种配置都立即提交并完成 CAS，之后再迁移其余
成员，保留故障恢复边界。等待循环使用栈上原生句柄数组，监听 park、signal
及迁移后的所有者退出事件。

源阶段信号先退休登记并重启入口、重新复制绝对超时；迁移后信号返回
EAGAIN，SA_RESTART 不改变这个结果。绝对超时支持 MONOTONIC 和
CLOCK_REALTIME，取得锁的已提交所有权优先于取消。普通 wake/requeue 拒绝
PI 源和目标等待行，并跳过关系及恢复日志元数据。

记录仍为 72 字节。队列 section、guard、park/event 及 magic 升级到 v4；
PI 任务表升级到 v3，隔离旧版运行时的队列和捐赠图。不同版本的运行时必须
使用各自版本的共享域，不能据此声称它们可以互相唤醒。

入口错误顺序、nr_wake 必须为 1、1 + nr_requeue 额度、等待者 TID、目标
WAITERS 位、私有目标读写故障以及部分成功后返回错误，参照
[Linux 6.12 重排队实现](https://github.com/torvalds/linux/blob/v6.12/kernel/futex/requeue.c)
及 [sys_futex 入口](https://github.com/torvalds/linux/blob/v6.12/kernel/futex/syscalls.c)。

## 本次验证

以 main 4a011e7 为基础合入本批改动，从成功的 Cargo JSON 冻结完整原生
依赖图。在 KINAKAZE_FUTEX_OPT=0/1 下各通过 libc 636 项、pthread 59 项，
零失败；分别忽略 19、4 项已有性能/子进程助手测试。生产 release 编译检查
通过（8.95 秒），固定镜像 SHA-256 在测试前后相同。

新增 10 项 raw syscall 边界测试和共享记录角色检查，覆盖空队列目标读取、
私有目标校验顺序、WAITERS 位、忙目标零额外额度、五等待者批量额度、
既有目标 FIFO、后续错误保留已完成前缀、代理写故障恢复源登记、源/目标
两阶段超时以及迁移前后信号与 SA_RESTART。保留前一阶段的实际优先级
捐赠/恢复测试、四个真实子进程崩溃时点、客体探针和基准入口。

原始日志、构建图、全部镜像和源文件 SHA-256 见
[验证记录](measurements/futex-pi-requeue-2026-10-01.json)。较早的默认配置专项
运行未作为双配置证据。首次结果整理器因子进程多行输出误判，但原 libc
运行本身 636 项全通过；修正匹配后复用该成功日志并补齐其余三次运行。

队列仍有 32,768 条记录，PI 任务表仍有 4,096 项。源绑定计入队列额度；
源行死亡时同时回收绑定，代理获取日志保护中的目标行保留给恢复流程。

## 尚待验证和后续工作

此前 main 的 PI 重排队客体探针及基准保留在
[前一阶段记录](futex-requeue-pi-2026-10-01.md)，对应原 v3 协议。本次未重新
构建或执行真实 Debian 图，也未测量新批量路径的性能收益；此前图的结果
不能替代当前 v4 图的客体验证。独立映射别名、跨进程只读/失效目标恢复、
权限竞争及耗尽路径仍需扩展专门验证。

pthread PI 属性、Linux 实时策略、跨 PID namespace 层级的所有者视图仍需
接入或完善。全部 375 个 syscall、3,750 项路径审查保留待验证状态。

## 最终 main 集成

实现提交 3424d6a 随后合入 e48261a 的最新 main（含 1.1.0 发布），得到
0965bd3。四处 syscall 入口冲突来自旧分支格式差异，保留本批已验证的 PI
入口规则，并保留其他发布变更。合并后的 release 生产编译检查通过
（11.28 秒）。上述 636/59 原生结果对应合并前固定图；没有把生产编译检查
当作对最终发布图重新执行整套运行测试的证据。
