# GNOME 第四轮瓶颈分析（2026-09-26）

还有可分析、压缩的开销，但本轮没有确认新的稳定提速。保留第三轮生产启动器；事件通知、提前激活辅助服务和切换新版运行库都只作为实验留在工件目录，没有替换默认行为。

## 当前关键路径

相同旧分发、测试根和第三轮启动器，四次交替对照中的基线全部启动成功，中位数 **3.426 秒**。各段分别取中位数，不能要求它们相加恰好等于整体中位数。

| 阶段 | 中位耗时 | 解释 |
| --- | ---: | --- |
| 宿主启动至 Shell exec | 1.297 秒 | 包含 worker、session bus、Python/GI、private system bus、IBus |
| 其中：IBus 启动后等待就绪 | 0.614 秒 | 是上一行的子阶段；保留 daemon 存活和总线名称检查 |
| Shell exec 至 Mutter 运行日志 | 0.438 秒 | 包含新进程、依赖装载、链接及原生初始化 |
| Mutter 运行至 Shell startup-complete | 1.710 秒 | 包含 GJS、JS 模块、UI、背景与主循环 |

`detail-1` 使用实际 GResource 模块的客体单调时间标记，整次启动 3.393 秒：

- `main-gi-ready` 至模块导入完成：**0.301 秒**。
- 模块导入完成至 `main.start()` 返回：**0.438 秒**。其中 `WindowTracker` 附近的初始化段约 91 毫秒，Panel 约 191 毫秒，二者不是纯粹的单函数 CPU 时间。
- `main.start()` 返回至 startup-complete：**0.383 秒**，包括初次主循环、背景准备和布局/启动动画路径。测试根已关闭动画，但该路径仍需准备背景与布局。
- AccountsService 构造附近的初始化段仅 **7.4 毫秒**；没有重复启动 IBus 的诊断标记。第三轮消除的两个等待没有重新出现。

Mutter 日志至第一个上述 JS 标记仍有约 0.66 秒的未细分区间。它涉及标记之前的原生/GJS 初始化，当前证据不能把它全部归为 JS 导入、磁盘或渲染。该估算混合宿主日志接收与客体时间间隔，只适合定位，不能作为精确函数计时。

| map 累计 | 104.230 毫秒 | 整次运行，157 次 |

这些 span 有包含关系，不能把表中各项相加。采样会读取时钟、打开日志并写入记录，解释了为什么采样值不能直接代替正常运行的 0.438 秒。代码准备已经命中缓存：157 次 cache-read，处理约 142 MB 字节；没有证据支持“缺缓存，重新生成一次就能大幅提速”。IO 计数也不等于物理磁盘读取量。

## 尝试与结果

### IBus 事件通知

实验用 `Gio.bus_watch_name_on_connection` 唤醒 GLib 主循环，替代每 100 毫秒一次的同步 NameHasOwner 轮询；保留进程退出、启动期限和就绪后存活检查。真实 Shell、直接启动应用、自动激活服务环境、IBus panel 名称和输入上下文检查均通过。

早期小样本看似更快，因此继续做四组交替对照，顺序为 A1/B1/B2/A2/A3/B3/B4/A4：

| 配对 | 当前版 A（秒） | 事件通知 B（秒） |
| --- | ---: | ---: |
| 1 | 3.418 | 3.398 |
| 2 | 3.426 | 3.466 |
| 3 | 3.551 | 3.854 |
| 4 | 3.425 | 4.529 |
| 中位数 | **3.426** | **3.660** |

两组均 4/4 启动成功。B4 在 IBus 启动后的等待达到 1.692 秒；不能证明长尾由事件通知改动造成，也不能把前两次的几十毫秒差解释为稳定收益。**不合入。**

额外试验在事件通知版上提前异步激活 `org.a11y.Bus`，两次为 3.270、3.304 秒；同一探索阶段的事件通知版为 3.219、3.308 秒。没有显著收益证据，保留为实验。

### 已有新版原生运行库

保持生产启动器，比较 `startup-extreme4-20260926/final-dist` 与已有 `java-near-native-20260926/final-dist`。新版之前在其他用例中验证过并行启动、完整哈希与大型页面准备优化，但这不等于 GNOME 自动获得同等收益。

三组探索性对照全部启动成功，旧版 8.438/3.921/5.156 秒，新版 4.758/4.338/4.183 秒。相邻样本多段耗时同时变化，且没有这一批的宿主 CPU 采样，**不足以给出可信的 GNOME 提速比例或归因**。新版的真实 Shell、应用与 IBus 集成检查通过；本轮没有据此替换原来的分发。

## 稳定性和下一处值得追的开销

本轮一次旧版探索基线 `pilot-a1` 在 Shell exec 前因 IBus 退出 255 而失败，日志完整保留，没有按 0 秒计入速度。第三轮也观察到过这种失败，根因尚未确定。

核对安装组件为 IBus 1.5.27。上游代码表明 daemon 在运行主循环前启动 config、emoji extension、XIM 等组件，session bus 名称也通过异步注册取得；因此“等待 IBus 就绪”不仅是轮询休眠，还包含子进程与 IPC 初始化。退出 255 本身不足以定位哪一步失败。参考 [IBus 1.5.27 main.c](https://github.com/ibus/ibus/blob/1.5.27/bus/main.c) 和 [server.c](https://github.com/ibus/ibus/blob/1.5.27/bus/server.c)。

继续优化应优先分解 IBus 子进程创建/就绪过程与偶发退出，以及 Mutter 到首个 JS 标记之间的初始化；装载器的依赖图、重定位与代码准备是另一个已量化目标。需要更细的时间证据后再改动；仅缩短轮询、移动完成日志或跳过输入就绪，不能证明桌面实际更快可用。

## 测试边界与工件

共 **24 次受控运行**，其中 23 次完成 Shell 启动，1 次为上述 IBus 失败，包含诊断和集成测试，不作为一个统一性能样本集。全部使用独立非输入 Windows 桌面，没有调用 SwitchDesktop；内层 24 秒限制，独立 Job watchdog 27 秒。最长整次运行及清理 **9.929 秒**，全部清理后的活动进程数为 **0**。

测试保持同一 root、时区、locale、缓存与偏好；每次新建会话，OS 文件缓存已热且未受控清空。终点为 Shell startup-complete 日志；未验证首帧与物理键鼠输入。生产启动器与本轮开始时的副本逐字节相同，没有合入未证实有效的改动。
