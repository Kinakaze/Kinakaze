# 注册表绑定细分诊断

R27 基于已修复原生符号链接的 `ff12782`，仅在独立副本的 provider 绑定代码中增加计时区段。四轮真实 dpkg 小型诊断全部通过，冻结的 1951 个源码输入和 61 个分发文件未变化。该构建没有合入生产，诊断时间不能充当完整安装成绩；180 秒目标仍未达到。

| 区段 | 样本数 | 中位数 µs |
| --- | ---: | ---: |
| worker 加载运行时 DLL | 141 | 4413 |
| 注册表发现 | 137 | 1356 |
| 注册表绑定 | 137 | 800 |
| 已请求模块的元数据展开 | 76 | 1030 |
| 符号转换 | 76 | 110 |
| fork 模块登记 | 76 | 2 |
| 元数据展开后的 DLL 加载 | 76 | 1 |
| provider 初始化 | 76 | 0 |

元数据展开包含需要时的 DLL 加载，因此后续加载接近零不意味着首次加载免费。延迟绑定发生在实际需要模块时，样本数和注册表构建不同，不能把中位数相加。

旧 R20 的注册表绑定中位数为 8270 µs，本轮为 800 µs，但这不是生产优化收益。旧版在每个模块路径查询和共享 DLL 加载周围逐个写入计时日志；`StartupSpan::drop` 每次重新打开日志并写入，父区段包含这些子区段的日志开销。两次运行的主机条件也不同。旧日志仍保留，但其父阶段耗时不足以支持预计能节省同等生产时间的判断。

下一项候选来自实际 DLL 导入表：运行时依赖 VFS，而 VFS 仅因 FIFO 私有存储目录查询静态导入 `SHGetKnownFolderPath` 和 `CoTaskMemFree`，使普通 worker 提前加载 Shell32 和 Ole32。可测试将相同 Windows API 的解析推迟到实际查询时；仍须验证真实已知目录、FIFO 行为、重复使用开销和完整安装，不能用环境变量替代已知目录 API。

完整原始统计、证据哈希和 DLL 依赖见[测量记录](measurements/provider-binding-diagnostic-2026-10-01.json)。
